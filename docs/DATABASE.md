# Database

PostgreSQL, accessed through Drizzle ORM, behind repository interfaces so the provider can be
replaced without touching feature code.

## Drivers

One schema, one set of migrations, three interchangeable drivers:

| Driver   | Used for                                                        | Selected by                                                         |
| -------- | --------------------------------------------------------------- | ------------------------------------------------------------------- |
| `neon`   | Netlify production                                              | `JARVIS_DB_DRIVER=neon`, or a `DATABASE_URL` containing `neon.tech` |
| `pg`     | Any hosted PostgreSQL (Supabase, RDS, a Neon pooled endpoint)   | `JARVIS_DB_DRIVER=pg`, or any other `DATABASE_URL`                  |
| `pglite` | Local development, unit and integration tests, end-to-end tests | No `DATABASE_URL`, or `JARVIS_DB_DRIVER=pglite`                     |

PGlite is a real PostgreSQL compiled to WebAssembly, so local and test databases run the _same_
migrations and the _same_ SQL as production. `buildConfig` refuses to select it in production.

## Migrations

Generated by drizzle-kit from `src/server/db/schema.ts`, applied by a small driver-agnostic runner
(`src/server/db/migrate.ts`) that records applied files in `_jarvis_migrations` and is safe to run
on every deploy.

```bash
npm run db:generate     # after editing schema.ts — writes drizzle/NNNN_name.sql
npm run db:migrate      # applies anything pending, using the configured driver
```

The embedded PGlite database migrates itself when the server first opens it — it is created per
process, so migrating it from a separate CLI invocation would leave the running server with an
empty schema. Hosted databases are shared, so they are migrated explicitly by the command above.

Commit the schema change and the generated SQL together. Netlify runs `npm run db:migrate` as part
of the build command, before `next build`.

## Tables

### Core

| Table             | Purpose                                                                                                                                                                                                                                                                                |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projects`        | The registry. Name, type, status, phase, goal, priority, target date, tags, links, timestamps, plus denormalised `freshness` and `needs_attention` so list queries stay cheap.                                                                                                         |
| `project_sources` | A project's connections. `kind` is `github_repo`, `manual` or `external_link`. GitHub columns carry the observed repository state and per-source sync status, error and capability lists. Modelled as a one-to-many relationship so multiple repositories per project remain possible. |

### Owner-managed detail

`goals`, `milestones`, `blockers`, `decisions`, `manual_updates`, `next_actions` — all scoped to a
project, all carrying `provenance` and `source_system`, all cascading on project delete.

### Evidence and history

| Table              | Purpose                                                                                                                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `evidence`         | Every observed fact. Unique on `(project_id, source_system, kind, external_id)` — this is what makes synchronisation idempotent.                                                                            |
| `status_snapshots` | Historical assessments, including the narrative and the fingerprint. Never overwritten, so "what changed" always has a baseline.                                                                            |
| `sync_runs`        | One row per source per synchronisation: status, per-category results, error, rate limit.                                                                                                                    |
| `sync_locks`       | Cooperative per-project locks with an expiry, so a killed invocation cannot wedge a project.                                                                                                                |
| `activity_log`     | The audit spine: created, updated, status/goal/phase changed, blocker added/resolved, decision recorded, sync started/completed/failed, briefing generated, archived/restored, exported, retention applied. |

### Application

`sessions` (opaque token hashes only), `oauth_states` (single-use, short-lived), `app_settings`
(owner preferences), `query_history` (recent command-bar queries).

## Indexing

Indexes exist for the queries the product actually runs:

- `projects`: status, type, archived_at, needs_attention, updated_at, freshness, and a
  case-insensitive unique index on name.
- `evidence`: the identity unique index, plus `(project_id, observed_at)` for the timeline,
  `kind`, and `source_id`.
- `status_snapshots`: `(project_id, generated_at)` and `(project_id, fingerprint)`.
- `sync_runs`: `(project_id, started_at)` and status.
- `activity_log`: `(project_id, created_at)`, `created_at`, `kind`.
- `project_sources`: a partial unique index on `(lower(owner), lower(repo))` where
  `kind = 'github_repo'`, which enforces duplicate-import prevention in the database rather than
  only in application code.

## Conventions

- Every instant is `timestamp with time zone`, written in UTC. Calendar dates (target dates, due
  dates) are `text` in `YYYY-MM-DD`, because they have no time or timezone.
- Enumerations are `text` refined by a TypeScript union and validated by Zod at the boundary. This
  keeps migrations additive when a later phase introduces a new source or evidence kind.
- JSON columns (`tags`, `links`, `metadata`, claim arrays) are `jsonb` with typed accessors.

## Retention

Settings → _Your data_ applies a retention window to snapshots and activity. **Evidence is never
deleted by retention**, so historical claims keep their sources. The scheduled sync also purges
expired sessions and OAuth states.

## Backups

Use your provider's backups — Neon offers point-in-time restore; Supabase and RDS have scheduled
backups. Settings → _Export everything as JSON_ produces a portable copy of projects, evidence,
snapshots, sync history and activity, and deliberately contains no sessions or credentials.
